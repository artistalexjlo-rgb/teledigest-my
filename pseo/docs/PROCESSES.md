# РЕЕСТР ПРОЦЕССОВ VPS + ВЕСЬ СТЕК СТРАНИЦ — единственный источник правды

## ПОЛНЫЙ СТЕК (от мухи до прода; «процессов вне этой схемы не существует»)

```text
ПОСТОЯННО (реестр ниже):
  бот bots-grab (docker) ── граббер чатов → SQLite
       └─ экстрактор: сообщения → мухи ai_lesson   [Gemini flash-lite, учёт gemini_quota]
       └─ embed → Qdrant                            [gemini-embedding-2, свой RPD]
  bge-sweep.timer (2ч) ── мухи → local_vec.db/Qdrant-local  [ЛОКАЛЬНАЯ модель, без Gemini]
  sentinel (cron /6ч) ── HTTP-сторож портала, чирик при поломке [без Gemini]

ПО ОТМАШКЕ (руками, nohup на время прогона, умирает по завершении):
  1. facet.py <geo>            тег+ru-перевод [рот facet] + карв семей [carve] → out_facet/
  2. facet.py <geo> --assign-tail   хвост → полки×типы [assign]
  3. dedup.py <geo|--all> [--kratko]  дедуп-группы (KEYLESS, bge) + короткий ответ [kratko]
  4. lang_runner.py            переводы по очереди языков → out_facet_<lang> [translate, labels]
  5. questions_page.py         вопрос-контур → out_questions [questions]

СБОРКА/ДЕПЛОЙ (KEYLESS, одна команда с десктопа):
  ship.py = pull(VPS) → pages.py(json) → render.py(HTML) → readycheck(гейт)
            → git push multyspeak-pages → Cloudflare Pages → info.multyspeak.online
```

⚠️ Строка «СБОРКА/ДЕПЛОЙ» описывает тракт, который работает ТОЛЬКО с десктопа ассистента, и
его последнее звено больше не проходит: Cloudflare Pages отвергает деплой больше 20 000
файлов, а у нас 41 630 страниц. Принятая замена — раздел «ПУБЛИКАЦИЯ БЕЗ АССИСТЕНТА» ниже.

Все Gemini-вызовы билдера — ТОЛЬКО через `keybroker.call` (капы ртов: facet 1500 · carve 300 ·
assign 300 · kratko 600 · translate 400 · labels 200 · questions 300; поверх них — per-key
шаг/RPD и вина-vs-среда). Мимо мозга запросов не существует.

**Правило (2026-07-20, после инцидента pseo-runner):** на VPS имеет право жить ТОЛЬКО то,
что есть в этой таблице. Новый юнит/таймер/крон = явное «да» юзера + строка здесь В ТОМ ЖЕ
заходе. Всё, чего в таблице нет, — сносится при первой сверке. Сверка (`systemctl
list-timers`, `crontab -l`, running services) — в начале каждой рабочей сессии.

**Контекст инцидента:** юнит `pseo-runner.service` (авто-тегание, «удобная автоматика»)
был заведён 6 июля вне git и вне доков, пережил все уборки и три недели молотил ключи,
пока юзер считал, что «ничего не работает». 2026-07-19 он выел 1764 гранта за день и
устроил 429-фон. Самоходных демонов у билдера НЕ СУЩЕСТВУЕТ КАК КЛАССА: весь тракт
(facet → dedup → pages → render → ship) — по отмашке.

## ПУБЛИКАЦИЯ БЕЗ АССИСТЕНТА — принятая схема (2026-08-10)

**СТАТУС: решено, НЕ реализовано.** Читать как задание, а не как описание работающего.
Заказ юзера дословно: «мне нужен путь работающий без тебя, готовый, не процесс кодирования».

**Почему сегодняшний тракт этого не даёт.** Рендер сайта живёт только на десктопе
ассистента: в образе пульта есть мозг (`facet`, `dedup`, `facet_lang`, `keybroker`), но нет
`pages.py`, `render.py`, `templates/`, `i18n/`, `static/`. Пока рендера там нет, публикацию
физически может запустить только ассистент — и упирается это в рендер, а не в хостинг.

**Целевая схема — кнопка в Телеграме:**

- сайт = **каталог на диске хоста** (`/srv/pseo/<домен>/`), ВНЕ контейнеров: редеплой
  любого приложения страниц не касается;
- **пульт** (`bots-luky-rodzkl`) получает рендер-половину и шаг «Публикация» в
  `pipeline_steps()`, каталог сайта монтируется ему на запись;
- **новое приложение Dokploy**: Source Type `Docker`, образ `nginx:alpine`, тот же каталог
  на чтение, домен `info.multyspeak.online`, порт 80, лимит памяти. Сборки у этого
  провайдера нет — задавать нечего;
- оба домена = ДВА прогона одного рендера с разными `PSEO_DOMAIN` / `PSEO_CTA_URL` в разные
  каталоги (переменные уже есть, копий логики не нужно);
- рендер пишет в `<каталог>.new`, затем переименование: 41 630 страниц пишутся минутами, без
  подмены сайт всё это время был бы наполовину старым;
- `PSEO_OUT` — новая переменная каталога вывода в `render.py` (одна строка), чтобы писать
  сразу в маунт, а не копировать после;
- git остаётся **историей и бэкапом, не транспортом**: `step_pull`, `_pull_mature`,
  `step_push` в схеме не участвуют. Cloudflare — только DNS и кеш.

**Островков всего три:** каталог, приложение nginx, запись DNS.

**Чего НЕ делать (перечислено, чтобы не выдумывалось заново):**

- не собирать Docker-образ из корпуса — именно это положило РФ-сервер 2026-08-09 вместе с
  ВПН, переводчиком, инфо-порталом и БД. Ложится сборка, не отдача;
- не совмещать сайт и пульт в одном контейнере: рестарт бота гасил бы сайт, и наружу
  смотрел бы контейнер с ключами Gemini. Юзер этого и не просил;
- не заводить хостовых скриптов, systemd-юнитов и крона — реестр выше это запрещает;
- не тащить релизы, симлинки, `--link-dest` и nginx-`map`: отброшено как страховка от
  проблем, которых у нас нет.

**Порядок работ (по коммитам, каждый — ветка и PR):**

1. перенос рендер-половины в `pseo/combine/` + `jinja2` в `requirements.txt` + фикстура
   «в образе есть всё, что нужно рендеру»;
2. `publish.py` в комбайне: `pages.py --all` → `readycheck` как гейт → два рендера →
   переименование → сводка числами;
3. шаг «Публикация» в `pipeline_steps` (одно место: оттуда и кнопка, и цепочка) + сторожа:
   пишет в маунт а не в `/app`, два рендера с разными доменами в разные каталоги, нет
   корпуса — шаг молчит а не падает, каталог равен корпусу — шаг не зовёт;
4. README комбайна: новый Directory Mount и лимит памяти точными полями.

**Руки юзера, однажды:** два маунта на один каталог (пульту RW, nginx RO), приложение
nginx, запись DNS. Дальше — только кнопка.

**Открыто:** 996 редиректов из `_redirects` — это фича Pages, на nginx не работают, решать
отдельным заходом. Лимит памяти пульту ставить ПОСЛЕ первого замера рендера в контейнере —
замера нет, наугад не ставить.
